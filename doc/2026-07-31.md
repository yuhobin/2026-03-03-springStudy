## 1. Spring Security 개요

Spring에서 **인증(Authentication)** 과 **인가(Authorization)** 를 담당하는 보안 프레임워크

- **인증** : 사용자가 누구인지 확인 (로그인)
- **인가** : 인증된 사용자가 해당 자원에 접근할 권한이 있는지 확인 (권한 체크)

모든 요청은 DispatcherServlet에 도달하기 전에 **Security 필터를 먼저 통과**한다.

---

## 2. 동작 흐름

```
클라이언트 요청
      │
      ▼
Security 필터          ← 권한 확인
      │
      ├── 권한 있음 → DispatcherServlet → HandlerMapping → Controller
      │
      └── 권한 없음 → 403 접근 거부 (또는 로그인 페이지로 이동)
```

**예시**

| 요청 URL | 권한 | 결과 |
|---------|------|------|
| `/member/login.do` | 누구나 | 통과 |
| `/admin/admin.do` | ROLE_ADMIN만 | 일반 사용자 → 403 |
| `/board/list.do` | ROLE_ADMIN 또는 ROLE_USER | 비로그인 → 로그인 페이지 |

## 3. 권한(접근 제어) 설정

`<intercept-url>` 태그로 URL 패턴별 접근 권한을 지정한다.

```xml
<http auto-config="true" use-expressions="true">
    <intercept-url pattern="/member/**" access="permitAll"/>
    <intercept-url pattern="/admin/**"  access="hasRole('ROLE_ADMIN')"/>
    <intercept-url pattern="/board/**"  access="hasAnyRole('ROLE_ADMIN','ROLE_USER')"/>
    <intercept-url pattern="/**"        access="permitAll"/>
</http>
```

**주요 접근 표현식**

| 표현식 | 의미 |
|--------|------|
| `permitAll` | 누구나 접근 가능 (비로그인 포함) |
| `authenticated` | 로그인한 사용자만 접근 가능 |
| `hasRole('ROLE_ADMIN')` | 해당 권한을 가진 사용자만 접근 가능 |
| `hasAnyRole('ROLE_ADMIN','ROLE_USER')` | 나열된 권한 중 하나라도 있으면 접근 가능 |

> ⚠️ `intercept-url`은 **위에서부터 순서대로 적용**되므로 구체적인 패턴을 먼저 작성해야 한다.

## 4. 로그인 처리

`<form-login>` 태그로 로그인 관련 설정을 한 곳에서 처리한다.

```xml
<form-login
    login-page="/member/login.do"
    login-processing-url="/member/login.do"
    username-parameter="userid"
    password-parameter="userpwd"
    always-use-default-target="false"
    authentication-success-handler-ref="loginSuccessHandler"
    authentication-failure-handler-ref="loginFailureHandler"
/>
```

| 속성 | 역할 |
|------|------|
| `login-page` | 커스텀 로그인 페이지 URL |
| `login-processing-url` | 로그인 form action URL (Security가 자동 처리) |
| `username-parameter` | 아이디 input name |
| `password-parameter` | 비밀번호 input name |
| `always-use-default-target` | 로그인 후 항상 기본 페이지로 이동할지 여부 |
| `authentication-success-handler-ref` | 로그인 성공 시 실행할 핸들러 Bean |
| `authentication-failure-handler-ref` | 로그인 실패 시 실행할 핸들러 Bean |

**성공 / 실패 핸들러**

```xml
<beans:bean id="loginSuccessHandler" class="com.sist.security.LoginSuccessHandler"/>
<beans:bean id="loginFailureHandler" class="com.sist.security.LoginFailureHandler"/>
```

- 로그인 성공 → 사용자 정보를 **Session에 저장** 후 핸들러 실행
- 로그인 실패 → 실패 핸들러에서 에러 처리 (실패 메시지 전달 등)

## 5. 로그아웃 처리

```xml
<logout
    logout-url="/member/logout.do"
    invalidate-session="true"
    logout-success-url="/main/main.do"
/>
```

| 속성 | 역할 |
|------|------|
| `logout-url` | 로그아웃 요청 URL |
| `invalidate-session` | 로그아웃 시 Session 전체 무효화 여부 |
| `logout-success-url` | 로그아웃 완료 후 이동할 URL |

## 6. DB 연동 인증

`<jdbc-user-service>`로 DB에서 사용자 정보와 권한을 조회해 인증에 활용한다.

```xml
<jdbc-user-service
    id="userService"
    data-source-ref="ds"
    users-by-username-query="
        SELECT userid AS username, userpwd AS password, enable
        FROM springMember WHERE userid=?
    "
    authorities-by-username-query="
        SELECT userid AS username, authority
        FROM authority WHERE userid=?
    "
/>

<authentication-manager>
    <authentication-provider user-service-ref="userService">
        <password-encoder ref="bcryptEncoder"/>
    </authentication-provider>
</authentication-manager>
```

- Security가 요구하는 컬럼명(`username`, `password`)으로 **AS 별칭** 처리 필수
- 사용자 정보 테이블과 권한 테이블을 **분리해서 관리**하는 것이 일반적
- `authentication-manager` : 조회된 사용자 정보로 인증을 최종 처리하는 관리자

## 7. 비밀번호 암호화

Spring Security는 평문 비밀번호 저장을 허용하지 않으며, **BCrypt 암호화**를 권장한다.

```xml
<beans:bean
    id="bcryptEncoder"
    class="org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder"
/>
```

- BCrypt는 같은 문자열이라도 암호화할 때마다 다른 해시값을 생성 (Salt 적용)
- Security가 로그인 시 입력 비밀번호와 DB 암호화 값을 자동으로 비교 처리

## 8. CSRF 방어

```xml
<csrf disabled="true"/>
```

- **CSRF(Cross-Site Request Forgery)** : 사용자 의도와 무관하게 위조된 요청을 보내는 공격 기법 (파밍)
- 기본값은 활성화이며, 운영 환경에서는 `disabled="true"` 사용 지양
- 학습/개발 환경에서는 편의상 비활성화하고 진행

### 배운 점
- Security 필터가 DispatcherServlet보다 먼저 동작하기 때문에, 권한이 없는 요청은 Controller에 도달하기 전에 차단된다는 흐름을 이해함
- `<jdbc-user-service>`의 쿼리에서 Security가 요구하는 컬럼명(`username`, `password`)으로 반드시 별칭 처리해야 한다는 점을 실습을 통해 확인함
- BCrypt는 같은 비밀번호라도 매번 다른 해시값을 생성하므로 DB가 탈취되어도 원문을 알 수 없다는 점에서 보안상 중요한 역할임을 이해함
- `intercept-url`은 순서가 중요하며 위에서부터 매칭되므로 구체적인 패턴을 먼저 선언해야 한다는 점을 이해함
