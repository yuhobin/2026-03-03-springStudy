## 1. Spring MVC 핵심 구성 요소

Spring의 핵심은 **DI(Dependency Injection)** 와 **AOP(Aspect Oriented Programming)** 이며,  
MVC 동작은 아래 4가지 컴포넌트가 순서대로 협력해서 처리한다.

| 순서 | 구성 요소 | 역할 |
|------|---------|------|
| 1 | `DispatcherServlet` | 모든 요청의 진입점. `HttpServlet`을 상속받아 요청을 받고 흐름을 제어 |
| 2 | `WebApplicationContext` | Bean(라이브러리 + 사용자 정의 클래스) 전체를 생성·관리하는 컨테이너 |
| 3 | `HandlerMapping` | `@GetMapping` / `@PostMapping` 등을 탐색해 해당 Controller 메서드 호출 |
| 4 | `ViewResolver` | Controller의 return 값(View 이름)을 받아 실제 JSP를 찾고 데이터 전달 |

> 1~4는 모두 **라이브러리로 제공**되므로 개발자가 직접 구현할 필요 없음

## 2. 전체 동작 흐름

```
클라이언트 요청 (예: /main/main.do)
        │
        ▼
DispatcherServlet                 ← HttpServlet을 상속, 요청 수신 및 흐름 제어
        │
        ▼
 ── WebApplicationContext ───────────────────────────────────
       │                                                    
       ▼                                                    
  HandlerMapping                                            
  @Controller 클래스와 매핑 어노테이션을 탐색               
  → 해당 메서드 호출                                        
       │                                                    
       ▼                                                    
  Controller 메서드 실행                                    
  model.addAttribute("key", data)  ← 데이터 등록           
  return "main/main"               ← View 이름 반환        
       │                                                    
       ▼                                                    
  ViewResolver                                              
  return 값으로 JSP 파일 경로 결정                          
  → model에 등록된 데이터를 request에 담아 JSP로 전달       
 ────────────────────────────────────────────────────────────
        │
        ▼
      JSP                         ← model 데이터를 꺼내 화면 렌더링
        │
        ▼
클라이언트 응답
```

## 3. Model의 실체

Spring에서 사용하는 `Model`은 내부적으로 `HttpServletRequest`를 감싼 객체다.

```
Model
  └── HttpServletRequest request   (보안상 직접 노출하지 않고 Model로 추상화)
        └── addAttribute(key, obj)
              = request.setAttribute(key, obj)
```

- `model.addAttribute("key", data)` 는 결국 `request.setAttribute()`를 호출하는 것
- Model을 사용하는 이유 : `HttpServletRequest`를 직접 노출하지 않고 **보안성과 코드 가독성**을 높이기 위함
- ViewResolver가 JSP로 forward할 때 Model에 등록된 데이터가 함께 전달됨

## 4. 개발자가 직접 만드는 부분

Spring MVC에서 1~4번 구성 요소는 라이브러리가 처리하므로, 개발자는 아래만 작성하면 된다.

```
개발자 작업 영역
  ├── @Controller        ← 요청 처리 및 View 이름 반환
  │     └── Model        ← View에 전달할 데이터 등록
  ├── JSP (View)         ← 화면 렌더링
  └── Model 계층
        ├── VO           ← 데이터 구조 정의
        ├── DAO          ← DB 접근
        └── Service      ← 비즈니스 로직
```

> Spring MVC의 핵심은 **복잡한 요청 처리 흐름을 프레임워크가 대신 처리**해주고,  
> 개발자는 비즈니스 로직(Controller, Service, DAO)과 화면(JSP)에만 집중할 수 있다는 점이다.

## 5. Transaction

### 1) 개념

하나의 작업 단위 안에서 실행되는 여러 DB 연산을 **모두 성공(commit)하거나 모두 실패(rollback)** 처리하는 것.  
예) 입고 insert + 재고 update → 둘 다 성공해야 commit, 하나라도 실패하면 rollback

### 2) @Transactional 이전 - 직접 처리

트랜잭션을 직접 구현하면 모든 메서드에 동일한 연결·커밋·롤백·해제 코드가 반복된다.

```
getConnection()          ← @Before   : 커넥션 획득
conn.setAutoCommit(false) ← @Around(전) : 자동 커밋 해제
  입고()
  재고()
conn.commit()            ← @Around(후) : 정상 처리 시 커밋
conn.rollback()          ← @AfterThrowing : 예외 발생 시 롤백
conn.setAutoCommit(true)
disConnection()          ← @After    : 커넥션 반납
```

### 3) @Transactional 적용 후

```java
@Transactional
public void insert() {
    입고();
    재고();
}
```

- 위의 커넥션 관리·커밋·롤백 코드를 Spring이 AOP로 자동 처리
- 개발자는 **핵심 비즈니스 로직만** 작성하면 됨
- XML 설정 : `<tx:annotation-driven/>` 추가 시 `@Transactional` 활성화

### 4) Transaction과 AOP의 관계

`@Transactional`은 AOP로 구현되어 있다. 2)번의 커넥션 처리 단계가 각각 AOP의 JoinPoint 시점과 정확히 대응된다.

| 트랜잭션 처리 단계 | AOP JoinPoint |
|-----------------|--------------|
| `getConnection()` | `@Before` |
| `setAutoCommit(false)` | `@Around` (전) |
| `commit()` | `@Around` (후) |
| `rollback()` | `@AfterThrowing` |
| `disConnection()` | `@After` |

### 배운 점
- DispatcherServlet이 단순한 서블릿이 아니라 전체 MVC 흐름을 조율하는 **Front Controller** 역할임을 이해함
- `model.addAttribute()`가 결국 `request.setAttribute()`와 같은 동작임을 알게 되면서, 기존 Servlet 학습과 연결됨
- `@Transactional`이 단순한 어노테이션이 아니라 AOP의 JoinPoint 시점을 활용해 커넥션 관리 전체를 자동화한 것임을 이해함 → AOP 개념과 트랜잭션이 자연스럽게 연결됨
